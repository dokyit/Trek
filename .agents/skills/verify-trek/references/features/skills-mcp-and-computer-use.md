# Skills, MCP, and computer use

## What it does

Discovers agent skills across supported homes, lets users enable/disable them, and configures Trek’s built-in computer/simulator/browser/delegation tools plus additional MCP servers (browser use: see [Browser](browser.md)). The composer exposes matching `$` skill mentions.

On the Mac, computer use works **in the background** by default (Settings → Tools & MCP → Computer use → Work in the background): the agent picks one window (`open_app` opens an app behind the user's windows; `screenshot` with a `window_id` picks an open one), sees just that window even when covered, and its clicks, keys and scrolls go to that window's app alone. The user's pointer, keyboard and front app are untouched. `open_app` never starts a second copy of an app: a running app's frontmost window is used (one with no window gets a reopen; `new_window: true` asks it for one more with cmd+n), and only an app that isn't running is launched, by the path of its best copy (/Applications first, build output last), with a window that comes forward put back behind. The app in front is the user's while they're at the Mac, reading included: `open_app` (with `new_window` too: a second window of the same app would take their keys) and every click or key there are refused with a message to ask them, and Trek shows "Waiting: you're using …". They're away when the screen is locked (or another user's session is in front), the display is asleep, the screen saver is on, or they've given no input for 5 minutes (input background use posts itself doesn't count). The agent's window stays its own on another Space, a full-screen one included: it's captured from the window server's own copy (`SLSHWCaptureWindowList`; `screencapture -l` gives nothing there) and input goes to it as usual, with a note that it's out of the user's sight. A window that's listed but not yet on screen (just opened) gets 3 s to show; a minimised window, a hidden app's or a closed one is let go and said as such (`desktop/spaces.rs`). When a click, key or typing makes the agent's app raise a window over the user's (and the user gave no input since), the user's window is put back in front; another app reordering its own windows is never touched. Text is typed a character a key event (an event carrying several makes apps like Calculator keep only the first). `trek-mcp` and the iPhone helper (`trek-phone-helper`, iPhone Mirroring taps) never check themselves in as an app (no `GetProcessForPID` or other Process Manager call; process serial numbers come from `lsappinfo`, and tests fail on such a call), so neither shows as a second Trek in the Dock. `trek-mcp computer` (with `TREK_COMPUTER_MODE=background`) reports each step to Trek over the session's IPC channel (`computer_activity`), and Trek shows it in a floating picture-in-picture window: the agent's window live, where it last pointed, what it's doing and for which thread. The picture has Stop (the thread's turn ends, as its own Stop does), folds to a pill or is put away, and comes back from the menu bar icon (Show Background Use), the command palette, or the thread's working bar ("… in the background · Show"). It closes a few seconds after the turn ends.

**Elements.** The agent reads its window before it looks at it: `elements` gives the window's accessibility tree as an outline, as the Browser's `browser_snapshot` gives a page. One line per element: role, name, value (never a secure field's: it isn't read), state (`[disabled]`, `[focused]`, `[selected]`, `[checked]`/`[unchecked]`, `[expanded]`/`[collapsed]`, `[offscreen]`), its frame (`[frame=x,y,width,height]`, in the pixels of the window's screenshot, so the x/y tools agree with it), and a ref (`[ref=e12]`) on each one that can be acted on. `filter` (role or name contains), `interactive_only` and `max` (150; past it "N more not shown") narrow it; `menu_bar` adds the app's menus and their items, read without opening anything (the Apple menu is left out, and a menu's title can't be pressed since that would open it on the user's screen: its items can). The reading is bounded: 3,000 elements, 60 levels, 5 s (as long again for the menus), 2 s for any one answer; a reading that stopped early says so and why (and is never taken to show that something has gone), and a table gives the rows that show. By ref: `press` asks the element for its own accessibility action (`press`, `show_menu`, `increment`, `decrement`, `confirm`, `cancel`), which makes no pointer or key event and gives nothing the focus; `click` with a `ref` clicks the element's centre through the same background path as a click at x/y, for controls that ignore the press action; `type_text` with a `ref` gives the field the focus first (asked through accessibility, else by a click in it), types only once the field says it has it, and says what the field then holds; `wait` with `text` or `element` (and `gone`) looks until it shows or goes, at most `timeout_ms`, and answers with the window's fresh outline either way. An element keeps its ref while it stays (it's the same object, by `CFEqual`), and a ref is acted on only after the element at its place in the tree is found again and proven the same: that object, the same role and name, about where it was (its centre within half its smaller side, 4 to 24 points). Anything else is refused with what changed and "read the elements again"; a ref from another window's elements is refused too. What can't be known is said as unknown and never tried again: a press the app didn't answer in time (one that opens a dialog often ends so), text typed into a field that reads as before. Chromium and Electron apps build their tree only for a client that asks, so the first `elements` of such an app turns it on, for that app alone: `AXManualAccessibility`, else `AXEnhancedUserInterface` when the app's bundle has a Chromium renderer helper (Chrome 157 takes only the second). A window on a Space that isn't showing isn't among its app's `AXWindows`: it's found as the app's main or focused window, else by its element token (`_AXUIElementCreateWithRemoteToken`, bounded). Nothing here activates an app, raises a window, moves the pointer or takes the keyboard; Trek's own windows are never read or acted in; the user's front app can be read (the reply says it's theirs) but `press`, `click` and `type_text` there are refused like any other input. A background app answers accessibility slowly when the Mac is busy: readings that take 0.05 s took seconds, and were cut at the limit, under a load average over 20. In front mode the same tools work on the window in front, with frames in full-screen screenshot pixels and the real pointer and keyboard for `click` and `type_text`. Windows has no elements yet: the tools aren't listed there.

## Reach it as a user

Open **Settings → Skills** to scan/filter/toggle skills. Open **Settings → Tools & MCP** to inspect built-ins and add or remove MCP server commands. Type `$` in a composer to choose an enabled skill.

## Reach it with the CLI

```sh
./.agents/skills/verify-trek/scripts/trek-dev open settings:skills
./.agents/skills/verify-trek/scripts/trek-dev screenshot skills
./.agents/skills/verify-trek/scripts/trek-dev open settings:tools-&-mcp
```

The isolated profile may discover project skills but does not launch a real agent to consume them. Adding/removing MCP configuration is intentionally not automated by this verification CLI.

Background use's picture can be checked with the mock, which reports steps the way `trek-mcp computer` does (nothing is clicked for real). Give it a real window's id and size in points (any app's, from `CGWindowListCopyWindowInfo`) so the picture has something live to show, and don't wait for the turn, or the picture will have closed:

```sh
./.agents/skills/verify-trek/scripts/trek-dev send --no-wait "mock:background <window id> 800x600 Safari"
./.agents/skills/verify-trek/scripts/trek-dev send --no-wait "mock:background <window id> 800x600 Safari waiting"   # waits 6 s first
./.agents/skills/verify-trek/scripts/trek-dev control background-use fold     # or unfold, hide, show, toggle, next, stop
```

The picture is a window of its own (layer 101), so `trek-dev screenshot` doesn't include it. It opens on the Trek Test Display with the rest of the run (bottom right, as on a real screen): `trek-dev screenshot <name> --real --display` shows it beside the main window, and `trek-dev windows` lists its id for `screencapture -l <its window id>`. The working bar's chip does show in `trek-dev screenshot`. To check `trek-mcp computer` itself in the background, run it over stdio with `TREK_COMPUTER_MODE=background` against a throwaway window (a TextEdit file, or Chrome with a `--user-data-dir` in /tmp) and confirm the front app and the pointer never change, that `pgrep` finds one process of the app, and that `lsappinfo list` never lists the `trek-mcp` pid (a Dock icon). That last holds for the `trek-mcp` inside Trek's bundle, which is the one that matters (`./bin/agent-cli dock` says "one Trek"); a `trek-mcp` run from anywhere else, a build from the repo or the released binary copied out, is listed as `BackgroundOnly` (no Dock icon) from its first `type_text` on, and not before: reading elements and `press` never list it. For elements, in the same session: `elements` (with a `window_id`), `press` a checkbox or a menu item by its ref and read it again, `type_text` with the text area's `ref`, `wait` for the text; in Chrome, `press` a page's button and `type_text` into a page's field by ref. The user may be moving the pointer themselves, so sample it every few milliseconds through each call: a tool that warped it would show as one large step to the element's place on screen. Three things to know before starting, all met on 2026-11-09: Chrome comes to the front when launched with a window, `open -g` or not, so start it with `--no-startup-window` and let `open_app` ask it for one (which still came up over the front window: the reply says so); a first launch of Chrome wakes the user's Google updater; and a window that opens on the user's own Space can be clicked by them (a sheet was dismissed that way mid-check).

## Code

`crates/trek-app/src/settings_view.rs`, `settings_view/pages.rs`; skill discovery in `crates/trek-core/src/skills.rs`; built-in tools in `crates/trek-mcp/src/` (background input in `desktop/skylight.rs`, where an off-screen window is in `desktop/spaces.rs`, a window's elements and their own actions in `desktop/ax.rs`, the outline and its refs in `outline.rs`, shared with the Simulator, the window-by-window tools in `computer.rs`); the picture-in-picture window in `crates/trek-app/src/background_use.rs`.

## Verify

This `verify-trek` skill appears with its description, toggles persist, `$` results match enabled skills, MCP rows report actionable startup failures, and removal affects only the selected server. Background use: the picture opens at the screen's bottom right without taking focus, follows each step (its caption and the pointer), folds and unfolds, is put away and brought back, stops the agent with its Stop, and closes after the turn; the working bar's chip says where the agent works. Elements: the outline names what the window shows with frames that match its screenshot, a ref stays the same across readings while its element stays, a pressed checkbox reads as checked afterwards, text typed by ref is in the field, a ref to something that has gone or changed is refused with nothing done, and through all of it the front app is the same and the pointer makes no jump.
