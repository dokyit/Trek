# Browser

## What it does

Embeds a web browser beside the thread with navigation, zoom, element picking, page screenshots sent to the composer, and developer tools.

Agents use it too (**browser use**): every session gets Trek's `trek-browser` MCP server (`trek-mcp browser`, Settings › Tools & MCP › Browser › Browser tools, on by default), whose tools drive this tool's real page while the user watches. It is Trek's browser-use option for every agent that takes MCP servers (Claude Code, Codex, ACP agents, OpenCode, the mock); there is no other backend to choose. The calls travel over the session's Trek channel (as the sub-agent tools' do) to the main window's Browser, which runs them one at a time:

| Tool | Arguments | Notes |
|---|---|---|
| `browser_open` | `url`, `new_tab?` | waits for the load (20 s); a blank new tab takes the page |
| `browser_tabs` / `browser_switch` / `browser_close` | `tab` (id) | |
| `browser_back` / `browser_forward` / `browser_reload` | | |
| `browser_snapshot` | `interactive_only?` | an accessibility outline (role, name, value, state, `-> href`) with stable refs (`[ref=e12]`, kept as `data-trek-ref`), through open shadow roots and same-origin frames, plus title, URL and scroll |
| `browser_click` / `browser_hover` | `ref` | pointer and mouse events, then `element.click()`; reports a navigation or a new tab |
| `browser_type` | `ref`, `text`, `submit?`, `clear?` | focus, key events per character, text through `execCommand('insertText')` (falls back to the prototype's value setter plus an input event), so React/Vue state sees it |
| `browser_press` | `key`, `ref?` | `Enter`, `Shift+Tab`, `Control+A`, `PageDown`…, with the browser's default actions (Enter submits by the default button, Tab moves focus) |
| `browser_select` | `ref`, `option` | a `<select>` by label or value; an ARIA combobox is opened and its option clicked |
| `browser_scroll` | `direction?`, `amount?`, `ref?` | the window, or the biggest box that scrolls when the window doesn't |
| `browser_wait` | `text` / `selector` / `ms`, `gone?`, `timeout_ms?` | polls, at most 60 s |
| `browser_screenshot` | `full_page?` | an image; a full page is stitched from screens (12 at most). Needs the Browser on screen |
| `browser_text` | | the main content's text |
| `browser_eval` | `js` | an expression or statements that return; promises awaited |

While an agent works the panel shows a strip, "Agent is using the browser · <thread> · <last action>", with **Stop**: the user takes the browser back, the call under way fails at its next step and that turn's later calls fail with "The user took over the browser…" (its next turn may use it again; **Hand back** ends it at once). The element each action touches is outlined in the page for a moment ("Agent · Click"). With Settings › Tools & MCP › Browser › **Show the browser live** on, the Browser comes forward when the agent of the thread in view starts using it (at most once in five minutes, like the Simulator's); off, a Browser tab is made behind the one in front.

Approvals follow the thread's access level and use the thread's own approval card (Deny / Always allow / Allow): typing into a password field and `browser_eval` ask unless the thread has Full access; submitting a form to another origin and downloads (`<a download>`) ask in Supervised and Auto-accept edits. Opening and reading pages never ask. Claude Code and Codex aren't asked by their own permission prompts for these tools: Trek asks where it should.

**Ad blocker** (the user's own uBlock Origin; nothing of it ships with Trek): ⋯ › **Import uBlock Origin…** or Settings › Tools & MCP › Browser › Ad blocker takes its folder (macOS also a .zip/.crx). On macOS its declarativeNetRequest rulesets (and its bundled lists' site-specific `##` element hiding) become WebKit content rules (`browser_adblock/convert.rs`), kept in `<data>/adblock/rules.json` and compiled once into `<data>/adblock/compiled` (a list is looked up by a hash of its JSON: a restart or toggle finds it in ~1 ms; an import or an allowed site compiles, 5–20 s for uBlock Origin 1.75's 35,864 rules). The menu then has **Block ads (uBlock Origin)** (on/off) and **Allow ads on <site>** (shows at once: the tab goes without the lists and reloads while they recompile with the site let through); Settings shows "35,864 rules → N active, M skipped (redirects as blocks)", **Re-import** and **Remove**. On Windows the folder is copied beside WebView2's extensions and installed as a Manifest V2 extension (Edge runs MV2 until its 2027 phase-out), then managed on the Extensions page.

**Popups and sign-in** (macOS; `panels/browser/webkit.rs`, `asks.rs`, `prompts.rs`). Each view's WebKit UI and navigation delegates are wrapped in Trek's own, which pass what they don't answer to wry's. `window.open` and `target=_blank` get a real view made from the configuration WebKit hands over, so the popup shares cookies and storage (the default, persistent `WKWebsiteDataStore`) and keeps `window.opener` (`postMessage`, `opener.location`, `popup.closed` all work). As in Safari, a `target=_blank` link implies `rel=noopener` (its tab has no `window.opener` unless the link says `rel=opener`), and a page that sends `Cross-Origin-Opener-Policy: same-origin` is cut off from its opener; Google's `gsi/transform` sends COOP only as report-only. A popup that asks for a size (`window.open(url, name, 'width=500,height=600')`, as Google's sign-in does) opens as a **sheet** over its opener's place: its title and site, **Show as a tab** and **Close** (`browser-sheet`, `browser-sheet-tab`, `browser-sheet-close`); one that doesn't is a tab. `window.close()` closes it and its opener comes back to the front. ⌘-click and middle-click open a link in a new tab, without an opener. On Windows a popup still opens as a plain tab without `window.opener` (WebView2's `NewWindowRequested` can hand the page a view of Trek's through `SetNewWindow`; not done yet), so a sign-in that posts back to its opener can't finish there.

Why Google sign-in stopped at `accounts.google.com/gsi/transform`: Google Identity Services' button opens a popup (`display: popup`, `redirect_uri: gis_transform`, `response_mode: form_post`); after the account is chosen the popup POSTs to `/gsi/transform`, whose page hands the credential to `window.opener` with `postMessage` and closes. Trek used to refuse every `window.open` (wry's handler answered `Deny`) and load the URL in a new tab instead: that tab had no opener, so `gsi/transform` had nobody to give the credential to and sat blank. The user agent was never the problem: the view sends Safari's own (`… Version/<installed Safari> Safari/605.1.15`, no `wv` or app token), `navigator.webdriver` is false, and Google serves WKWebView with that agent the pages it serves Safari. WebView2 sends Edge's agent unchanged.

**What pages ask** shows in a bar above the page (`browser-ask`, buttons `browser-ask-no` / `browser-ask-yes`; a tab behind with one waiting has a dot): `alert`, `confirm` and `prompt` (the page waits, as in Safari; wry left them silent: `alert` did nothing, `confirm` was false); camera and microphone ("<site> wants to use your camera and microphone", Don't Allow / Allow: wry granted every request unasked); location (WebKit's own `_webView:requestGeolocationPermissionForOrigin:…` hook); and a link only another app opens (`mailto:`, `zoommtg:`, `x-apple…`, a `trek://` link into Trek itself, an OAuth redirect to an app's scheme): "<site> wants to open Zoom", Cancel / Open, or "…a foo: link, which no app on this Mac opens". A frame inside the page can't spring an app: only the page itself asks. Typed in the address bar, such an address goes straight to its app. While an agent's browser call is under way a page dialog is answered for it, as browser drivers do (OK to an `alert`, Cancel to `confirm` and `prompt`), and the call's answer says so: the page runs nothing, the agent's own scripts included, until a dialog is answered.

**Failed loads say why**, in Trek's words, on Trek's error page (`asks::load_failure`): the server can't be found, refused the connection (your own server isn't running), took too long, the Mac is offline, the certificate isn't valid, macOS's App Transport Security refused plain http, the ad blocker stopped it, too many redirects, or the error's domain and code. A load that became a download, went to another app or was replaced is not a failure. A page whose web content process ends is reloaded once; twice in a minute and the error page says it stopped working. A page that refuses frames (`X-Frame-Options`, `frame-ancestors`, COOP) loads normally at the top level.

**Downloads** (a `download` link, a response the view can't show, a redirect to a file) go to ~/Downloads (`name (1).ext` beside an existing one) with a toast, "Downloading <name>…" then "Downloaded <name> to Downloads"; a tab opened only for the download closes again.

**What WebKit can't do here.** Passkeys and security keys (`navigator.credentials` with `publicKey`): WebKit only offers WebAuthn to an app with Apple's managed web-browser entitlement (`com.apple.developer.web-browser.public-key-credential`) or associated domains for the site, so in Trek's Browser they fail with `NotAllowedError`; use the site's password or code sign-in, or ⋯ › **Open in Safari** (`browser-safari`), the escape hatch for any site that insists on a real browser. Web notifications: `Notification` exists, and WebKit itself answers `requestPermission()` with `"denied"` without a prompt (an app's web view can't post them), so sites carry on without. Camera and microphone: WebKit offers `navigator.mediaDevices` only to an app whose Info.plist explains both (the bundled Trek's does, `script/bundle.sh`) and asks macOS for the app's own access first (the system prompt, once), then Trek's bar per site. Location works the same way: WebKit asks macOS for the app's Location Services access before it asks the page's delegate, so it needs `NSLocationUsageDescription` and the hardened runtime's location entitlement (both in the bundle now). Without them (the driver's bare binary) a page's `getCurrentPosition` gets no answer at all, neither the bar nor an error; the bundled path is not checked live yet. Third-party cookies follow WebKit's defaults, as in Safari: blocked across sites (Intelligent Tracking Prevention), with the Storage Access API for embedded sign-in frames; storage is partitioned per top-level site. Google's own iframes (`gsi/iframe`, One Tap) behave as in Safari, which is why GSI uses the popup there. Universal links never leave the view on macOS (WebKit only opens apps for them on iOS). The file picker (`<input type=file>`) is wry's: an open panel that allows directories and multiple files when the input does. Clipboard reads (`navigator.clipboard.readText()`) follow WebKit's rules: a user gesture, and WebKit's own Paste confirmation for content from another app (not checked live here). Passkeys were not checked live either: the entitlement rule is Apple's documented one. Content blockers (tracker blocker, ad blocker) reach a popup a moment after WebKit starts its first load.

## Reach it as a user

Press ⌘J, choose **Browser**, enter a URL or search in the address field, and use the header controls for back/forward/reload, picker, screenshot, zoom, or devtools.

## Reach it with the CLI

```sh
./.agents/skills/verify-trek/scripts/trek-dev open tool:browser
./.agents/skills/verify-trek/scripts/trek-dev screenshot browser-panel
```

`control browser go <address>|back|forward|reload|state|snap <name>` drives the tool without a pointer; `control browser adblock-import <folder>`, `adblock on|off` and `adblock-allow` (macOS: the site in front) drive the ad blocker without its file picker (the driver's fresh settings start with it off; a compiled list stays in the profile's data folder): `state` writes `browser.json` (the page, the panel's area and the native view's rectangle), `snap` writes the page as WebKit (or WebView2) draws it to `<name>.png` in the shot folder, even with the window behind others. The GPUI screenshot leaves the native page blank; lay the snap over it at `area` to see both. `control click browser-scheme` cycles the page scheme (Auto, Light, Dark). `control browser focus|unfocus` gives the page the keys (as a click in it does) or takes them back; `control browser eval <js>` writes the page's answer, as JSON, to `browser-eval.json`; `control browser press cmd-v` (macOS) sends a real key event through AppKit (Trek comes to the front for it: a background app has no key window), so editing keys can be checked end to end. The clipboard is the Mac's own: save and restore it around such a check. Avoid shared authenticated sites during verification.

Popups, sign-in and asks, live (macOS): `crates/trek-app/src/panels/browser/fixtures/serve.py` serves pages on loopback that behave as a site with Google's button and as Google does (the opener on `127.0.0.1`, the identity provider's popup on `localhost`: two origins), and `check.py` drives them through the driver and checks each step, ending "Browser popups: all N checks passed." or what failed:

```sh
./.agents/skills/verify-trek/scripts/trek-dev start
./.agents/skills/verify-trek/scripts/trek-dev open tool:browser
python3 crates/trek-app/src/panels/browser/fixtures/check.py
```

By hand: `python3 crates/trek-app/src/panels/browser/fixtures/serve.py 47615`, then `control browser go http://127.0.0.1:47615/signin.html`, `control browser eval signIn()` (a sized `window.open`: `state`'s `all_tabs` has the popup with `opener` and `sheet: [500, 600]`, and it's `active`), `control browser eval window.__idp` (`opener: true`, `safari: true`, `webdriver: false`), `control browser eval "setTimeout(() => document.getElementById('f').submit(), 0), true"` (the form POST to `/transform`, which posts the credential to the opener and closes), then `control browser eval window.__check` on the opener (`credential: "test-credential-123"`, `from: "http://localhost:47615"`, `closed: true`). `tabs.html` has the rest: `target=_blank`, `window.open()` written into, `mailto:`, a scheme no app opens, a redirect to an app's scheme, a redirect to a download, a page that refuses frames, `alert`/`confirm`/`prompt`, camera and microphone, location and notifications; `control browser ask yes|no|text <words>` answers the bar, `state`'s `asks` lists what's waiting, and `control browser tab <id>` brings a tab to the front. A page held by a dialog answers no `eval` until the bar is answered, so start dialogs from a `setTimeout` and read the page only after `ask`. Camera and microphone are left out unless `TREK_CHECK_CAMERA=1`: the driver's bare binary has no Info.plist, so macOS's own camera check can take a minute. On a Mac under heavy load (a load average in the hundreds) a page can take most of a minute to answer an `eval`; the check waits up to four minutes per command. The real thing, only up to where credentials would go (never the user's own accounts): `control browser go https://claude.ai/login`, then `control browser eval "setTimeout(() => [...document.querySelectorAll('button')].find(b => /Continue with Google/.test(b.innerText)).click(), 0), true"`: Google's popup (`redirect_uri=gis_transform`, `response_mode=form_post`) opens as a 590×830 sheet on `accounts.google.com` showing "Sign in to continue to Claude", and `control browser eval !!window.opener` there is `true` (checked 2026-10-30).

Browser use, live (the Mac test of it): the mock serves a test site of its own and works through it with the real tools, checking each step, and ends with "Browser check: all 27 steps passed." or what failed.

```sh
./.agents/skills/verify-trek/scripts/trek-dev project /tmp/some-folder
./.agents/skills/verify-trek/scripts/trek-dev send "mock:browser" --timeout 240
./.agents/skills/verify-trek/scripts/trek-dev send --no-wait "mock:browser"   # then, mid-run:
./.agents/skills/verify-trek/scripts/trek-dev control browser snap mid        # the outlined element
./.agents/skills/verify-trek/scripts/trek-dev control click browser-agent-stop  # take over: later steps fail "took over"
./.agents/skills/verify-trek/scripts/trek-dev send --no-wait "mock:browser approvals"
./.agents/skills/verify-trek/scripts/trek-dev control click allow-session     # the password; then `allow` or `deny` for the script
```

`mock:browser <url>` opens that page and reads it instead. The tally is the thread's last answer (also in `data/trek.sqlite`, table `items`).

## Verify

A sign-in popup keeps `window.opener` and closes itself into its opener (the fixtures' check passes); sized popups are sheets, others tabs; dialogs, camera/microphone, location and app links wait on the bar; failed loads say why; downloads toast. Navigation and history update the address/title, picker identifies the intended element, page capture reaches the composer, zoom persists per tab, and devtools opens without crashing the app. Pages lay out at the panel's width (Google's responsive results, not its fixed-width legacy page: the view sends Safari's user agent) and follow the page scheme: `prefers-color-scheme` pages switch at once, Google's search pages a few seconds later (reloaded). ⌘C/⌘X/⌘V/⌥⇧⌘V/⌘A/⌘Z/⇧⌘Z work in a focused page (the page sees each key first), Trek's other shortcuts still win, and the editing keys go to Trek's own fields when the page doesn't have the keys. Browser use: `mock:browser` passes every step, the strip shows during the run and goes about 12 s after, Stop fails the rest of the turn's calls, and `mock:browser approvals` raises the password and script cards (none with the thread on Full access).
