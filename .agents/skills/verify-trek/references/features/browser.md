# Browser

## What it does

Embeds a web browser beside the thread with navigation, zoom, element picking, page screenshots sent to the composer, and developer tools.

Agents use it too (**browser use**): every session gets Trek's `trek-browser` MCP server (`trek-mcp browser`, Settings › Tools & MCP › Browser › Browser tools, on by default), whose tools drive this tool's real page while the user watches. It is Trek's browser-use option for every agent that takes MCP servers (Claude Code, Codex, ACP agents, OpenCode, the mock); there is no other backend to choose. The calls travel over the session's Trek channel (as the sub-agent tools' do) to the main window's Browser, which runs them one at a time:

| Tool | Arguments | Notes |
|---|---|---|
| `browser_open` | `url`, `new_tab?` | waits for the load (20 s); a blank new tab takes the page |
| `browser_tabs` / `browser_switch` / `browser_close` | `tab` (id) | |
| `browser_back` / `browser_forward` / `browser_reload` | | |
| `browser_snapshot` | `interactive_only?` | an accessibility outline (role, name, value, state, `-> href`) with stable refs (`[ref=e12]`, kept as `data-trek-ref`), through open shadow roots and same-origin frames, plus title, URL and scroll |
| `browser_click` / `browser_hover` | `ref` | pointer and mouse events, then `element.click()`; reports a navigation or a new tab |
| `browser_type` | `ref`, `text`, `submit?`, `clear?` | focus, key events per character, text through `execCommand('insertText')` (falls back to the prototype's value setter plus an input event), so React/Vue state sees it |
| `browser_press` | `key`, `ref?` | `Enter`, `Shift+Tab`, `Control+A`, `PageDown`…, with the browser's default actions (Enter submits by the default button, Tab moves focus) |
| `browser_select` | `ref`, `option` | a `<select>` by label or value; an ARIA combobox is opened and its option clicked |
| `browser_scroll` | `direction?`, `amount?`, `ref?` | the window, or the biggest box that scrolls when the window doesn't |
| `browser_wait` | `text` / `selector` / `ms`, `gone?`, `timeout_ms?` | polls, at most 60 s |
| `browser_screenshot` | `full_page?` | an image; a full page is stitched from screens (12 at most). Needs the Browser on screen |
| `browser_text` | | the main content's text |
| `browser_eval` | `js` | an expression or statements that return; promises awaited |

While an agent works the panel shows a strip, "Agent is using the browser · <thread> · <last action>", with **Stop**: the user takes the browser back, the call under way fails at its next step and that turn's later calls fail with "The user took over the browser…" (its next turn may use it again; **Hand back** ends it at once). The element each action touches is outlined in the page for a moment ("Agent · Click"). With Settings › Tools & MCP › Browser › **Show the browser live** on, the Browser comes forward when the agent of the thread in view starts using it (at most once in five minutes, like the Simulator's); off, a Browser tab is made behind the one in front.

Approvals follow the thread's access level and use the thread's own approval card (Deny / Allow for session / Allow): typing into a password field and `browser_eval` ask unless the thread has Full access; submitting a form to another origin and downloads (`<a download>`) ask in Supervised and Auto-accept edits. Opening and reading pages never ask. Claude Code and Codex aren't asked by their own permission prompts for these tools: Trek asks where it should.

What Trek asks rests on what its own script reads in the page (`probe` in `agent.js`: is this a password field, does this click or Enter send a form, and where to), so that script runs where the page can't reach it: a script world of Trek's own, which shares the page's document and nothing else (`panels/browser/isolated.rs`). macOS: a `WKContentWorld`; Linux: a WebKitGTK script world; Windows: a DevTools isolated world (`Page.createIsolatedWorld`, then `Runtime.evaluate` in it), with the page's own world as the fallback should the protocol refuse (then the script uses nothing it finds on `window`, and the log says so once). A page can't put its own commands in Trek's place or swap one, and what it does to its own `JSON`, `Element.prototype` or an element's own properties isn't what Trek's script sees. The probe reads what the browser will act on, not what the markup says: the field's type as the browser has it (and a text field drawn as dots, `-webkit-text-security`, counts as a password field), the control a click really lands on (the button around a clicked child, the control a label is for), the form it belongs to wherever it sits (`form=`), and the address the browser would send it to (`formaction`, the default button's for Enter). Each action then reads its element again as it acts and does nothing if it has since become a password field, a download or a form bound elsewhere ("The page changed what … does while Trek was checking it"). `browser_select`'s clicks on a list of the page's own are asked about like any click. What stays out of reach: what the page's own handlers do when the click or key arrives (a script that posts the fields somewhere itself), and state a custom element keeps only in the page's JavaScript. `browser_eval` runs the agent's script in the page's world, as it must to read the page's variables; its answer is the page's word, and no approval rests on it.

**Ad blocker** (the user's own uBlock Origin; nothing of it ships with Trek): ⋯ › **Import uBlock Origin…** or Settings › Tools & MCP › Browser › Ad blocker takes its folder (macOS also a .zip/.crx). On macOS its declarativeNetRequest rulesets (and its bundled lists' site-specific `##` element hiding) become WebKit content rules (`browser_adblock/convert.rs`), kept in `<data>/adblock/rules.json` and compiled once into `<data>/adblock/compiled` (a list is looked up by a hash of its JSON: a restart or toggle finds it in ~1 ms; an import or an allowed site compiles, 5–20 s for uBlock Origin 1.75's 35,864 rules). The menu then has **Block ads (uBlock Origin)** (on/off) and **Allow ads on <site>** (shows at once: the tab goes without the lists and reloads while they recompile with the site let through); Settings shows "35,864 rules → N active, M skipped (redirects as blocks)", **Re-import** and **Remove**. On Windows the folder is copied beside WebView2's extensions and installed as a Manifest V2 extension (Edge runs MV2 until its 2027 phase-out), then managed on the Extensions page.

**Blocking ads** (macOS; the page is the same on Windows): the built-in list (⋯ › **Block ad and tracker networks**, on by default) stops loads from the big ad and tracker networks only, so a site's own ads (YouTube's promoted tiles, its pre-roll, which come from youtube.com) stay; that menu row used to say "Block ads and trackers", which read as an ad blocker. Real ad blocking is uBlock Origin Lite, run by WebKit: while no ad blocker is installed and on (`catalog::ad_offer`: uBO Lite, uBO, AdGuard, Adblock Plus, AdBlock by store id), the Extensions page's first card is **Block ads on every site** (`browser-extensions-ads`, button `browser-extensions-block-ads`) and the ⋯ menu has **Block ads on every site…** (`browser-block-ads`, which opens the page and does the same). One click downloads it and shows its Install card (with a line on why it reaches every site); **Install** is the one confirmation. Installed, it runs at its own recommended mode, Optimal, on every site: its permissions are granted as installed, so `permissions.getAll()` has `<all_urls>` and it registers its scriptlets in both worlds (`scriptlets-main`, `scriptlets-isolated`) and its element hiding (`css-specific`), with all 6 default rulesets (18,988 rules: WebKit compiles them itself). Seen 2026-11-20 on macOS 27.2 with uBO Lite 2026.1116.1650: adblock-tester.com 41/100 → 100/100; youtube.com search for "vpn" lost its Sponsored tile (the `ytd-search-pyv-renderer`/`ytd-ad-slot-renderer` boxes are 0 px high); a watch page's player response has no `adPlacements`/`playerAds` and no pre-roll plays (with it off: a "Sponsored · 2 of 2" pre-roll); a feed tile holding `ytd-ad-slot-renderer` is `display: none` (its easylist rule; a signed-out feed shows no tiles to see it on). Its popup opens under its button, and the mode chosen there sticks (YouTube at Basic brings the pre-roll back, Optimal removes it). It all survives a restart. If install fails, the page says why and the log has `browser extensions: Downloading… failed: …`.

**Trek's ad blocker** (macOS, `browser_adblock/{lists,engine,scriptlets,page}.rs`, `cosmetic.js`; on unless ⋯ › **Block ads (uBlock Origin's lists)** `browser-blocker-toggle` turns it off, `settings.browser.blocker_off`): uBlock Origin's own default lists (its filters, badware, privacy, unbreak and quick fixes, EasyList, EasyPrivacy, the Online Malicious URL Blocklist and Peter Lowe's), fetched from where uBlock Origin fetches them into `<data>/adblock/lists` (each again after its interval: the quick fixes daily, most every four days; looked at every six hours while Trek runs; a list that can't be fetched keeps its last copy), with their `!#if` parts kept as uBlock Origin keeps them in Safari (`env_safari`; no HTML filtering). Brave's `adblock` crate (MPL-2.0, NOTICE) reads them: their network filters become WebKit content rules (242,002 filters → 237,857 rules in 2 lists under WebKit's limit, each list carrying every exception; WebKit compiled them in 6.7 s once, then finds them again at once by a key of the lists' text: a picked element doesn't recompile them), and the engine stays in memory for pages. As a tab's main frame starts to go somewhere (`browser/webkit.rs`'s navigation hook, before the document exists, as Brave's iOS browser does), `page.rs` gives the view the site's scriptlets (uBlock Origin's own, in the page's world at document start: YouTube's `json-prune`/`set-constant` fixes among them, 87 KB there) and `cosmetic.js` in a content world of Trek's (`TrekAdblock`) with the site's hiding (`display:none!important`), its procedural filters (`:has-text`, `:upward`, `:xpath`, `:matches-css`, `:min-text-length`, `:matches-attr`, `:matches-path`, `:remove()`, `:style()`, `:remove-attr()`, `:remove-class()`) and generic hiding asked of Trek as the page's classes and ids appear (`trekAdblock` handler). uBlock Origin's scriptlets and redirect resources come from its latest GitHub release (`<data>/adblock/ubo/<version>`, weekly): its scriptlet modules are put into one script (each module a function, imports a table) and read once by a hidden WebKit view (`trek-scriptlets.json`); none of it ships with Trek (GPLv3). **Allow ads on <site>** takes the lists and scripts off that site's pages at once (no compile). **Block an element…** (`browser-blocker-pick`) lets the user click one; `site##selector` joins `settings.browser.my_filters` and it goes at once. ⋯'s status line (`browser-blocker-status`): "9 lists · 242,002 network filters → 237,857 WebKit rules · 201 scriptlets (uBlock Origin 1.77.2)". While it's on, the uBlock Origin Lite offer (menu and Extensions page card) isn't shown. Cost, measured 2026-11-27 in the isolated app: per page 88–545 µs in the engine, under 1.2 ms with the scripts set; a restart's build 0.35 s off the main thread; Trek's own memory no different on or off (371 MB off, 366 MB on, after the same five pages). What WebKit's public content rules can't do: a `redirect` or `modify-headers` rule compiles but WebKit applies it only for an extension's list, so `$redirect=` filters block, and `$removeparam`, `$csp`, `$header`, `$permissions` and regular expressions WebKit can't run aren't applied (7,780 of the 242,002 network filters didn't convert); iframes of other sites get the lists' network rules and generic hiding but not their own site's scriptlets. Driver: `control browser blocker on|off`, `blocker-refresh` (fetch everything now), `blocker-hide <selector>` (the picker's line for the site in front), and `state`'s `blocker` (stats, `ready`, and the page in front: `hide`, `procedural`, `scriptlets_bytes`, `lookup_us`). Measured against the same pages before (built-in list only; uBlock Origin Lite) and after (Trek's blocker alone): adblock-tester.com 46 → 100 (uBO Lite 100); adblock.turtlecute.org 68% → 86% (uBO Lite 87%); canyoublockit.com's simple and extreme tests: the interstitial and 4–5 ad frames → none; forbes.com 44 ad/tracker requests, an ad frame and 3 slots → 1 first-party request, none shown; YouTube signed out: a pre-roll (`ad-showing`, one ad placement) → none, the video playing; a search's Sponsored tile → none.

**Extensions** (⋯ › **Extensions…**, Settings › Tools & MCP › Browser › **Extensions…**, or the address `trek://extensions`): one page on both systems (`panels/browser_extensions.rs`), in the page's place. Its search takes a name (filters the starter list; Enter on a single match installs it; a "Search the Chrome Web Store" row opens the store in a tab), a Chrome Web Store or Edge Add-ons link, or a bare id; **Folder…** takes an unpacked extension (run where it is, Chromium's id from its path or manifest `key`), **File…** a `.zip`/`.crx`. The page opens with the store link of the page in front filled in. A download (the store's CRX endpoint, `clients2.google.com/service/update2/crx`, CRX header stripped, `_metadata` dropped) or package waits unpacked in `<extensions>/.incoming/<id>` behind a card: "Install <name>?", what it will be able to do in words (`manifest::describe`), the starter list's verdict, **Cancel** / **Install**. The starter list (`browser_extensions/catalog.rs`: uBlock Origin Lite, Dark Reader, Grammarly, Bitwarden, 1Password, Vimium, Privacy Badger, React Developer Tools) says per extension "Works here", "Partly works" or "Doesn't run here" and why (measured under WebKit with Trek's shim, below: a background stops at the first API WebKit lacks). Measured 2026-11-27: uBlock Origin Lite, Dark Reader (a light page gets its dark scheme), Vimium (`f` shows its link hints), Privacy Badger (60 trackers on forbes.com, the ad networks among them blocked) and React Developer Tools (its panels, below) work; Bitwarden (its popup signs in as far as the master password), 1Password (its setup page) and Grammarly (its Sign in opens grammarly.com's sign-in in a tab) run up to where a real account is needed, which wasn't used. Before Trek's channel (below), Bitwarden and 1Password stopped without `chrome.notifications` and Privacy Badger at `chrome.webRequest.OnBeforeSendHeadersOptions`. Installed rows: icon, name, version or the first problem WebKit reported (red), Options (macOS), Permissions (what it can do and every error), on/off, Remove.

**Popups and sign-in** (macOS; `panels/browser/webkit.rs`, `asks.rs`, `prompts.rs`). Each view's WebKit UI and navigation delegates are wrapped in Trek's own, which pass what they don't answer to wry's. `window.open` and `target=_blank` get a real view made from the configuration WebKit hands over, so the popup shares cookies and storage (the default, persistent `WKWebsiteDataStore`) and keeps `window.opener` (`postMessage`, `opener.location`, `popup.closed` all work). As in Safari, a `target=_blank` link implies `rel=noopener` (its tab has no `window.opener` unless the link says `rel=opener`), and a page that sends `Cross-Origin-Opener-Policy: same-origin` is cut off from its opener; Google's `gsi/transform` sends COOP only as report-only. A popup that asks for a size (`window.open(url, name, 'width=500,height=600')`, as Google's sign-in does) opens as a **sheet** over its opener's place: its title and site, **Show as a tab** and **Close** (`browser-sheet`, `browser-sheet-tab`, `browser-sheet-close`); one that doesn't is a tab. `window.close()` closes it and its opener comes back to the front. ⌘-click and middle-click open a link in a new tab, without an opener. On Windows the same happens through WebView2 (`panels/browser/webview2.rs`): `NewWindowRequested` hands the page a view of Trek's made from its opener's environment (`SetNewWindow`), so the popup keeps `window.opener`; a sized one is a sheet, and `window.close()` (`WindowCloseRequested`) closes it. There Ctrl-click and middle-click tabs keep an opener (wry doesn't pass the click's details). `fixtures/check.py` drives `trek-dev.ps1` on Windows.

Why Google sign-in stopped at `accounts.google.com/gsi/transform`: Google Identity Services' button opens a popup (`display: popup`, `redirect_uri: gis_transform`, `response_mode: form_post`); after the account is chosen the popup POSTs to `/gsi/transform`, whose page hands the credential to `window.opener` with `postMessage` and closes. Trek used to refuse every `window.open` (wry's handler answered `Deny`) and load the URL in a new tab instead: that tab had no opener, so `gsi/transform` had nobody to give the credential to and sat blank. The user agent was never the problem: the view sends Safari's own (`… Version/<installed Safari> Safari/605.1.15`, no `wv` or app token), `navigator.webdriver` is false, and Google serves WKWebView with that agent the pages it serves Safari. WebView2 sends Edge's agent unchanged.

**What pages ask** shows in a bar above the page (`browser-ask`, buttons `browser-ask-no` / `browser-ask-yes`; a tab behind with one waiting has a dot): `alert`, `confirm` and `prompt` (the page waits, as in Safari; wry left them silent: `alert` did nothing, `confirm` was false); camera and microphone ("<site> wants to use your camera and microphone", Don't Allow / Allow: wry granted every request unasked); location (WebKit's own `_webView:requestGeolocationPermissionForOrigin:…` hook); and a link only another app opens (`mailto:`, `zoommtg:`, `x-apple…`, a `trek://` link into Trek itself, an OAuth redirect to an app's scheme): "<site> wants to open Zoom", Cancel / Open, or "…a foo: link, which no app on this Mac opens". A frame inside the page can't spring an app: only the page itself asks. Typed in the address bar, such an address goes straight to its app. While an agent's browser call is under way a page dialog is answered for it, as browser drivers do (OK to an `alert`, Cancel to `confirm` and `prompt`), and the call's answer says so: the page runs nothing, the agent's own scripts included, until a dialog is answered.

**Failed loads say why**, in Trek's words, on Trek's error page (`asks::load_failure`): the server can't be found, refused the connection (your own server isn't running), took too long, the Mac is offline, the certificate isn't valid, macOS's App Transport Security refused plain http, the ad blocker stopped it, too many redirects, or the error's domain and code. A load that became a download, went to another app or was replaced is not a failure. A page whose web content process ends is reloaded once; twice in a minute and the error page says it stopped working. A page that refuses frames (`X-Frame-Options`, `frame-ancestors`, COOP) loads normally at the top level.

**Downloads** (a `download` link, a response the view can't show, a redirect to a file) go to ~/Downloads (`name (1).ext` beside an existing one) with a toast, "Downloading <name>…" then "Downloaded <name> to Downloads"; a tab opened only for the download closes again.

**Passkeys** (macOS; `panels/browser/passkeys.rs`, `crates/trek-passkeys`). Trek's Browser has an authenticator of its own, because WebKit gives an app's web view none: WebKit answers `navigator.credentials` only in an app with Apple's managed entitlement `com.apple.developer.web-browser.public-key-credential` (granted by Apple on request to an organization's browser, and carried by a provisioning profile) or for the app's own associated domains. Trek is signed with its own certificate ("Trek Local Signing", `docs/RELEASING.md`), which no profile can cover, and an app that claims the entitlement without one doesn't launch. So, without Trek's authenticator, every page sees what WebKit leaves (measured 2026-11-26 on macOS 27.2, on webauthn.io in a tab with the setting off, and in a frame, which Trek doesn't answer): `PublicKeyCredential` and `navigator.credentials` exist, `isUserVerifyingPlatformAuthenticatorAvailable()` and `isConditionalMediationAvailable()` are `false` (while `getClientCapabilities()` claims everything, `passkeyPlatformAuthenticator` and `hybridTransport` included), and `create()` and `get()` reject at once with `NotAllowedError: The request is not allowed by the user agent or the platform in the current context, possibly because the user denied permission.` ("The document is not focused." when the page hasn't the keys). That `false` is GitHub's "This browser or device is reporting partial passkey support" (its banner shows when the API is there and the platform-authenticator check is falsy), and the rejection is why "Continue with passkey" never completed, on every site. With Trek's authenticator, github.com/login posts `webauthn-iuvpaa-support: supported`, the banner stays hidden, and **Sign in with a passkey** reaches Trek's bar.

What Trek does instead: before a view's first page loads it gets two scripts (main frame only). `passkeys_page.js`, in the page's world, replaces `navigator.credentials.create/get` for `publicKey` requests and the feature checks (`isUserVerifyingPlatformAuthenticatorAvailable()` → `true`, `isConditionalMediationAvailable()` → `true`, `getClientCapabilities()`), and makes real `PublicKeyCredential` objects of the answer; `passkeys_bridge.js` runs in a content world of its own (`TrekPasskeys`), the only world Trek's native handler (`trekPasskeys`, a `WKScriptMessageHandlerWithReply`) exists in, and passes the page's request on as text. Nothing the page says is believed: the origin is WebKit's own (`WKFrameInfo.securityOrigin` of the frame that sent the message), only the page itself is answered (a frame, of any origin, gets WebKit's refusal: WebKit doesn't tell Trek what a permissions policy allowed), and `trek_passkeys::parse` checks the request against that origin (https, or http on `localhost`; never an IP address; the rpId the page's host or a registrable suffix of it by the Public Suffix List, so not `co.uk`, `github.io` or `ample.com`). A request that fails that gets `SecurityError` and nothing shows.

Then the user decides, on a bar above the page (`browser-passkey`, buttons `browser-passkey-no` / `browser-passkey-yes#N`). Each line names the site first, then the account in quotes (the site wrote the account's name, so it is shown as one short line with nothing invisible in it): "On <site>: create a passkey for “<account>”?" with "Trek keeps it on this Mac and signs you in with it in this browser. It is not saved to iCloud Keychain or a password manager." (and "in place of the passkey it has for this account now" when it has one); "On <site>: sign in as “<account>”?"; with several accounts one button each; with none "On <site>: Trek has no passkey for this site" and how to get one (OK); for a passkey the site excludes "Trek already has a passkey for this account" (OK gives the page `InvalidStateError`, as the specification has it; Cancel tells it nothing). After Continue, macOS asks for Touch ID or the account's password, each time, and only then is anything made or signed.

What a page can learn from all this is kept to what it already knows. The page's view sits under the bar, so a page can measure the bar: it is one height (96 px) whatever it says, and its buttons take no click for the first 400 ms after what it asks changes. An autofill request (`mediation: "conditional"`) never touches the bar by itself: when Trek holds a passkey for the site a key appears in the toolbar (`browser-passkey-offer`, "Sign in to <site> with a passkey Trek keeps"), and the bar opens, with **Not Now** / **Sign In**, only when the user presses it; with no passkey nothing shows at all, and the page is the same size either way. Not Now puts the offer back on the key and leaves the page waiting, as an ignored autofill does. Every request that ends without a credential, however it ended (Cancel, no passkey, a refused Touch ID, the page gone), gets the same `NotAllowedError` with the same words. A request asked for silently (`mediation: "silent"`), a passkey a site would make without asking (conditional create) and a second request while one is on the bar are refused at once, the same whatever Trek keeps. A page's `AbortSignal`, a new page and a closed tab end the request; if that happens while Touch ID is up for a new passkey, the passkey is deleted again (the site never got it).

The keys: each passkey has a P-256 key made in the Mac's Secure Enclave (not added to the Keychain, which for enclave keys needs an entitlement too). The enclave's wrapped blob for it is kept in `<data>/passkeys/passkeys.json` (mode 600) with the site, the account and the public key; it is useless on another Mac, and on this one the enclave itself demands Touch ID or the password for every signature (the key's access control is `userPresence`), whoever holds the blob. A Mac with no Secure Enclave keeps the key in the login Keychain and Trek asks for Touch ID or the password first. What a site gets is standard WebAuthn: ES256, attestation `none` with Trek's own AAGUID (`947eb9e3-ba36-4630-b870-c909291ddd40`), a discoverable credential (the user handle comes back at sign-in; `credProps.rk` is `true`), flags UP and UV (plus AT at registration; never backup-eligible), a signature counter of 0 (as synced passkeys have, so a profile restored from a backup can't look like a cloned key), `authenticatorAttachment: "platform"`, transports `["internal"]`. One passkey per account per site: a new one takes the old one's place once its page has it (not before: a page that goes away mid-way leaves the old one working). The list is written whole, synced, beside a copy of its last state (`passkeys.json.bak`), which is read if the list itself is ever cut short.

These passkeys are Trek's own. They are not the ones in iCloud Keychain, Google Password Manager or 1Password, they don't sync, and "Delete all Trek data" deletes them. To use one: sign in to the site in Trek's Browser another way (password, a code), add a passkey in the account's security settings there (on github.com: Settings › Password and authentication › Passkeys › Add a passkey), and sign in with it from then on. Settings › Tools & MCP › Browser › **Passkeys** (also ⋯ › **Passkeys…**, `browser-passkeys`) has the switch (`browser-passkeys`; off, new tabs get WebKit's answer back) and the list: site, account, when added and last used, where the key is (Secure Enclave or Keychain), **Delete** (asks first; the site still lists the passkey until it's removed there).

Agents: a page an agent drives can ask for a passkey like any page, and the agent can't answer it. Trek's bar isn't in the page, so no browser tool or script reaches it, and a request that arrives while an agent's call runs, within 30 seconds of its last one, or during its turn goes to that thread's approval card instead ("<Agent> wants to: Sign in to <site> with your passkey for “<account>”"), at every access level, Full access included (`agent_core::Sensitive::Passkey`), and for as long as the agent's turn runs, however long the page waits before it asks. Allow covers that one request ("Allow for session" too: nothing is remembered), raising the thread to Full access with the card up doesn't answer it (`browser_use::asks_each_time`), and Touch ID still follows. An autofill request is never the agent's to raise: it sits behind the toolbar's key for the user. Deny, or a turn that ends, gives the page `NotAllowedError` or hands the question back to the bar.

Not there: passkeys from iCloud Keychain or a password manager (Apple's entitlement), security keys over USB or NFC and "use a phone" (the hybrid QR flow) — a site that asks for a security key (`authenticatorAttachment: "cross-platform"`) gets `NotAllowedError`; frames; `largeBlob`, `prf` and the `signal*` methods. Windows: WebView2 is Chromium and hands pages Windows' own WebAuthn (Windows Hello, security keys and a phone, through `webauthn.dll`); Trek adds and removes nothing there, and it has not been tried in Trek on a PC (`a_real_webview2_gives_pages_webauthn_of_its_own`, an ignored test, reads what a page sees). Linux: WebKitGTK has no WebAuthn (`ENABLE_WEB_AUTHN` is off in every release so far), so pages there have no `PublicKeyCredential`.

**What WebKit can't do here.** Passkeys kept in iCloud Keychain or a password manager, security keys and "use a phone": see **Passkeys** above; ⋯ › **Open in Safari** (`browser-safari`) is the escape hatch for a site that needs one of those, as for any site that insists on a real browser. Web notifications: `Notification` exists, and WebKit itself answers `requestPermission()` with `"denied"` without a prompt (an app's web view can't post them), so sites carry on without. Camera and microphone: WebKit offers `navigator.mediaDevices` only to an app whose Info.plist explains both (the bundled Trek's does, `script/bundle.sh`) and asks macOS for the app's own access first (the system prompt, once), then Trek's bar per site. Location works the same way: WebKit asks macOS for the app's Location Services access before it asks the page's delegate, so it needs `NSLocationUsageDescription` and the hardened runtime's location entitlement (both in the bundle now). Without them (the driver's bare binary) a page's `getCurrentPosition` gets no answer at all, neither the bar nor an error; the bundled path is not checked live yet. Third-party cookies follow WebKit's defaults, as in Safari: blocked across sites (Intelligent Tracking Prevention), with the Storage Access API for embedded sign-in frames; storage is partitioned per top-level site. Google's own iframes (`gsi/iframe`, One Tap) behave as in Safari, which is why GSI uses the popup there. Universal links never leave the view on macOS (WebKit only opens apps for them on iOS). The file picker (`<input type=file>`) is wry's: an open panel that allows directories and multiple files when the input does. Clipboard reads (`navigator.clipboard.readText()`) follow WebKit's rules: a user gesture, and WebKit's own Paste confirmation for content from another app (not checked live here). Content blockers (tracker blocker, ad blocker) reach a popup a moment after WebKit starts its first load.
